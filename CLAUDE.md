# Ghost: agent operating manual

Ghost is a voice-first assistant that triages GitHub issues and records decisions on them. It is a personal tool: one operator, running everything on one Linux workstation (ADR 0001). Ghost is the go-live name and the wake word; the original product documents use the working title VoiceTriage.

Before any non-trivial task, read:

1. [docs/architecture.md](docs/architecture.md) for the current design.
2. The ADRs in [docs/adr/](docs/adr/) for the area you are changing. They are short, and they are the rules.
3. [docs/original/](docs/original/) only for background. It assumes LiveKit Cloud and a TypeScript backend; where it disagrees with an ADR, the ADR wins.

## Status

First increment running on the workstation: generic write gate where everything runs unless the operator's permissions block it or ask first (no undo, ADR 0015; ADR 0034), apps connected to Ghost once as the only source of outside tools (ADR 0034; `~/.config/ghost/apps.json`, a catalog from the public app registry, sign-in, API keys and local packages; reads called directly, every other tool a change through the gate; `ghost-mock-github` stands in before a token exists; `docs/apps.md`) and kept up with as they change (ADR 0046; `ghost_core::apps`: an app's tool list is live and a session asks for it before every model call, a call may take 300 seconds and stops when the turn is cancelled, the operator hangs up or the session ends, a connection that died is opened again, a result is read whole within a budget of 24,000 characters, a description reaches the model up to 1,024 characters and the app's own instructions join its paragraph of the prompt, an app's resources and prompts are read tools, and past 40 tools or 30,000 bytes of schema only the pinned and the recently used are offered by name, the rest found with `ghost_tools_search`), voice pipeline with interceptor and processor slots, `ghostd` with transcript wake and the control API on a Unix socket (ADR 0013; `packages/api/openapi.json` is the contract for the TypeScript apps, regenerate with `make api-schema`), and named agents with their own persona, job, voice and memory (ADR 0014, where they are called conversations; `ghost_core::conversations`, rules named `conversations.*` in the permissions, an Agents screen in the desktop app; the one word to show is *agent*, see GLOSSARY.md), the Android app's screens in `apps/mobile` (`make android`, `make android-install`), and the phone transport on the daemon side (ADR 0016; `ghostd::phone`, a signed listener on the `GHOST_PHONE_LISTEN` addresses, WebRTC through `ghost_rtc` (str0m), `docs/phone-protocol.md`), reachable from anywhere through the operator's own WireGuard network (ADR 0020; no relay, no public listener), and hold (ADR 0021; "hang on, Ghost" keeps the session while the room talks, the name at the start of an utterance resumes it, nothing heard on hold is kept). Questions for the operator (ADR 0051; `ghost_core::questions`, a question is a waiting-list item with an answer, in the `questions` table): an agent, a run, an outside tool or a connected app asks (`ghost_ask`, `ask`, an app's one-field form through `AppAsker`), the operator answers in the desktop (Home, `/questions`, a notification's buttons), from the phone, or by voice (`ghost_answer`, the operator's own words only), and a question asked from a run starts one follow-up run once answered; a change waiting for a yes is the question Yes or No. The phone holds a signed live stream (`ghostd::phone::stream`, `GET /stream`, Server-Sent Events, snapshot then a cursor) and answers with signed requests once per `id`; the phone route is delivered on the phone's `seen`; the call route rings the phone (issue #22); an ntfy route carries a count. `docs/phone-protocol.md` is what the Android side is built from. Ghost's folder and its agents (ADR 0035, which retired departments; `docs/folder.md`, `docs/skills.md`): everything the operator edits is in `~/.config/ghost/`: the rules every agent reads (`AGENTS.md`, appended to only through `rules.add`), `apps.json`, `watches.json` and `hooks.json` (ADR 0027, ADR 0028; the desktop's Watching screen), `skills/`, `out/` (ADR 0033) and the agents under `agents/<slug>/`, hired and retired (`ghost_core.conversations`); every agent reaches every connected app, less what the operator's permissions block, and nothing narrows them per agent; skills are `SKILL.md` folders, Ghost's own then the operator's `~/.agents/skills` (`ghost_core::skills`); a skill's scripts run only through `ghost-scripts`, an app whose `run` is a change through the gate. Agents work on a schedule with nobody there (ADR 0047; `ghost_voice::headless`, `ghost_core::schedules`, `ghostd::schedules`): a run is a session's model and tools with no audio, through the same dispatcher and gate, for 30 model calls and ten minutes at the most, and it can be stopped; a change that resolves to `ask` in a run is set aside on the waiting list, never made; a schedule (`at`, `every` or `cron`, with an optional check that runs first with no model) is a row in SQLite, not a file in Ghost's folder, made by the operator (`/schedules` and `/runs` on the control API, the desktop's Watching screen) or by an agent through the gate; a watch may declare `act` and start a run for each new item; a run's answer is an item on the waiting list under `agent:<slug>` and a marked turn in the agent's transcript. Ghost is an app its own agents use (ADR 0045; `ghost_core::ghost_app`, served by the daemon in process and attached as the app `ghost`, never in `apps.json`): `ghost_docs_search` and `ghost_docs_read` over the documentation built into the binary, `ghost_status`, `ghost_audit_recent`, `ghost_apps_list`, `ghost_tools_search` (offered only past the limits on how many tools a turn carries, ADR 0046), `ghost_schedules_list`, and the changes `ghost_notify`, `ghost_resolve`, `ghost_waiting_ack`, `ghost_waiting_snooze` and `ghost_schedule_manage` (ADR 0047), through the gate and the operator's `ghost.*` permissions. The same app is served to the outside tools the operator connected (ADR 0048; `ghostd::outside`, a listener on the `GHOST_MCP_LISTEN` addresses, `127.0.0.1:47824` unless set, Streamable HTTP at `/mcp`; a client is a name and a token shown once and kept as a hash, `ghostd mcp add|list|remove` and Settings › Outside tools; `ghostd mcp serve --client <name>` bridges a tool that only starts commands; `docs/connect-ghost.md`), with `agents_list`, `agent_ask` (a written turn through the run with nobody there, ADR 0047: the same gate, a change at `ask` set aside, kept in the agent's transcript as asked by that tool), `say` and `events_wait` for them only, and the schedules as their own (`client:<name>` makes and manages only its own). The daemon is Rust (ADR 0039; one Cargo workspace with the desktop's shell, `crates/`), shipped inside the desktop app (ADR 0038; `make bundle`), with the ONNX Runtime 1.24.4 it was measured on in the bundle; the Python left is the tools (`tools/`, the version script and the scripts' tests; `tools/oracle`, the model wrappers the Rust was measured against, the aiortc far end, the wake tooling). Layout in [docs/architecture.md](docs/architecture.md#repository-layout). `make help` lists the developer entry points.

## Rules

- **Everything runs unless the operator's permissions say otherwise; the gate records every change** (ADR 0007, ADR 0011, ADR 0034). The model uses the tools it has: an app's read-only tools are called directly, and every other tool, like Ghost's own operations through `change`, goes to the gate in `crates/ghost-core`. The gate resolves the level from `[permissions]` in `~/.config/ghost/policy.toml` (`block`, `ask`, `quiet`, `allow` rules over an app, a tool or its arguments; the most careful match wins; `mode` is `open`, `ask` or `read-only` for what no rule names), and either runs the change now and Ghost says so, or waits for a spoken yes observed in the pipeline's own transcript; at `ask`, the operator's own request that plainly asks for that call is the yes (ADR 0017; the words come from the tool's name and short arguments, never from the app's description). Every level bounds the arguments, records the proposal and the outcome in the audit, and returns what the app answered. There is no undo: to reverse something Ghost asks for the opposite change (ADR 0015); don't add an undo path back. Never let a change reach an app except through the gate, never let a model set a permission, and don't add per-tool declarations or make Ghost ask by default: what is blocked or asked about is the operator's file. One default differs (ADR 0045): a change of Ghost's own app (`ghost.*`) that no rule names runs at `quiet` under the `open` mode, because the item it puts on the waiting list is the announcement; the operator's `block`, `ask` and `allow` rules and the other modes hold for it as for any app. A run with nobody there (ADR 0047) goes through the same gate under its own session id (`run-<id>`), and a change that resolves to `ask` in it is not made: it is set aside on the waiting list (ADR 0030) and the run carries on and says so. Nothing in a run is the operator's yes, and its instruction is never read as the request that plainly asks for a call (ADR 0017); don't let a run confirm its own change.
- **Confirmation classification is pluggable.** Jev when a key is configured, the regex allowlist otherwise, negation guard in both (`ghost_core::confirmation`, `ghost_core::jev`). For confirmation, Jev judges the operator's words inside a session only. A watch may also declare a typed Jev question over its parsed fields (#16), whose answer is one of the watch's declared values, with a declared default on failure. Jev is never on the passive audio path and never decides permission.
- **Issue and comment text is untrusted data, and so is anything an app sends**: tool descriptions, read-only hints, results, notices, and the catalog's text. None of it changes a permission or a prompt, and the model is told not to repeat it (a Mobbin tool description once had Ghost read a billing notice aloud). A tool that doesn't say it is read-only is a change. A connected app's text reaches the model within fixed bounds (ADR 0046, `ghost_core::apps::Limits`): a tool's description up to 1,024 characters with the schema's own property descriptions, what the app says about itself when it connects (its instructions) up to 2,000 characters in its paragraph of the prompt, its error message up to 300, and a result whole within a budget of 24,000 characters, cut at the end past that with a note saying how much was dropped (a list keeps 200 items; an image, a sound or a file is named with its type and size). All of it is redacted first and sits inside the sentence of the prompt that calls an app's words data. That is more than the first sentence and the 1,200 characters per string it replaced, and it widens what a hostile app can put in front of the model, so the defences stay as they were: no app text sets a permission, a rule or a prompt, and the gate asks or blocks by the operator's rules whatever the model was told. Don't raise a bound without saying what it costs on a turn (ADR 0018), and don't add a path that hands the model an app's text outside these bounds or unredacted. Ghost's own app (ADR 0045) is the one whose text is Ghost's: its descriptions reach the model whole and its results are not cut on the way out, since it caps them itself. That holds for Ghost's own text only: a tool of Ghost's own app that returns an app's text (`ghost_tools_search`) holds itself to the budget an app's result has.
- **Deterministic first, the model last.** Data from outside (a webhook, an observation, an app's result) passes through deterministic, tested code (verify, parse, constrain, check) before any of it reaches a model, and then only as typed fields. Where a check can't decide, a watch may declare a Jev question, then a model, in that order, each choosing only among values the operator declared. A schedule's check is the same rule (ADR 0047): one of an app's read-only tools called with no model, its result hashed, and the agent run only when the hash differs from the last run's; a check that fails is a failure, never a change. A watch may declare `act` (`"response": "act"` with an agent and an instruction in `watches.json`): a run for each new item, given the item's typed fields as data and nothing else the app sent, once per item and twelve times an hour at the most unless the block says otherwise. The operator declares it; no Jev or model step can choose it, and a webhook does not act. Don't put a model where a parser or a check will do.
- **A webhook is verified, parsed and checked before anything sees it** (ADR 0027). The listener runs in `ghostd` on its own addresses (`GHOST_HOOKS_LISTEN`) and shares no routes with the control API, the phone listener or the listener for outside tools. Each source's declaration ships recorded deliveries, good and bad, as fixtures that `ghostd check` runs. A public listener may take webhooks only: signature first (the body is not read until it passes), then the source's declared parser keeps typed, constrained fields and drops the rest, then the reference is re-read through one of the app's read-only tools (the permissions' block rules apply) before it is believed. Never hand a webhook's raw body to the model, never parse one with a model, and never let one write, confirm, or change a permission, rule or prompt. The phone path never goes through it (ADR 0020).
- **Idle audio stays on the machine.** In the passive state microphone frames go only to local models: today VAD plus Parakeet looking for a wake phrase (ADR 0010), later the ONNX wake model. Passive transcripts that contain no wake phrase are discarded immediately and are not logged or stored. Nothing is sent anywhere until the wake phrase fires. The one exception is `GHOST_DEBUG_AUDIO=1`, off by default: the operator sets it by hand for a debugging session, and it logs transcripts and audio decisions to the local journal or terminal only (`ghost_voice::debug`). Never turn it on in a committed config or unit file.
- **Outside tools come from apps the operator connects; there are no abilities and no declarations** (ADR 0034, superseding ADR 0022's declarations and ADR 0024's per-department servers). An app is an entry in `~/.config/ghost/apps.json` (`ghost_core::apps`): a URL Ghost signs in to (`ghost_core::signin`, OAuth with tokens in a 0600 file per app) or sends a key to, or a command it runs, passwords as `${NAME}`, filled from Ghost's vault when the app connects (ADR 0036). The desktop connects apps from Ghost's own copy of the public registry (`ghost_core::catalog`, refreshed at most hourly, never queried live on a turn). Every agent reaches every connected app. Every tool is offered under the app's name (`github_issue_write`); a name the model cannot take is rewritten, one that is too long or already taken gets a short hash, and which app a tool belongs to travels with the tool, never read back out of its name. The client keeps up with the app (ADR 0046): the tool list is live (listed again when the app says it changed, asked for before every model call, the list and the apps' paragraphs of the prompt replaced only when they differ, so don't cache a session's tools); a call may take 300 seconds and connecting 60 (`timeout`, `connect_timeout` per app) and a call must be stoppable: make it inside `ghost_core::apps::with_cancel` under the token of the turn, session or run it is for, so the app is told and the call returns an error, and never drop a change in the middle of the gate, which would leave a proposal with no outcome; a connection that died is opened again by the next call and in the background (`Apps::supervise`), a read cut off by it is made again, a change never, since the app may have made it; an app's resources and prompts are offered as reads (`<app>_list_resources`, `<app>_read_resource`, `<app>_list_prompts`, `<app>_get_prompt`) only when it advertises them; an app's question to the operator is declined until a real `Asker` is set. Past 40 tools or 30,000 bytes of schema across the apps only the pinned (`pinned` in `apps.json`) and the twelve most recently used or found are offered by name and the rest are found with `ghost_tools_search`; a hidden tool is still registered with the gate and can be called by name, since hiding is for the size of the prompt and never a permission, the same for every agent. Never add a capability by editing the daemon or the pipeline, and never write a bespoke client for a service: connect an app ([docs/apps.md](docs/apps.md)). One deliberate exception (ADR 0051): the ntfy route posts to the operator's ntfy topic with `reqwest` from the routes code, because a route the daemon starts must not wait on an app; its address and token are passwords named in `[routes]`, it sends a count and the kinds of source unless `carry = "title"`, and it reads nothing back. Don't add a second. The agents (`conversations`), the rules, the outputs, the skills, the waiting list's read and Ghost's fixed intents are the in-tree tool sources (`ghost_core::source::ToolSource`), and that list is closed.
- **Ghost's own functions come as tools of Ghost's own app** (ADR 0045, amending the rule above and "the model has no route to Ghost's state"). `ghost_core::ghost_app` is one MCP server (rmcp), served by the daemon to its own agents over an in-process pipe and attached as the app `ghost` (`App::attach`), so its tools take the same naming (`ghost_<tool>`), the same read or change split, the same gate, audit and permissions as any app's. To let an agent see or do something of Ghost's, add a tool there, with an honest `readOnlyHint`; never a new `ToolSource`, a branch in the pipeline, or a model's call to the control API. A tool never sets a permission, a rule, a watch or a prompt, and never returns a password, a passive transcript or audio. The calling agent comes from the session's dispatcher (`_agent`, `ghost_core::apps::CALLER_ARG`), never from an argument the model writes, and an agent resolves only the items it created. `ghost` is a reserved name: an `apps.json` entry cannot shadow it. The app starts before sessions can open, needs no vault, network or sign-in, and is never on the waiting list as not connected. The handler is `Clone` over shared state with nothing kept per connection, so the same one is served to outside clients (the next rule). Every tool is schema on every turn (ADR 0018): measure it (`ghosts_own_app::what_ghosts_own_tools_add_to_every_turn`) and say what a new one costs.
- **Outside tools reach Ghost through its own app, on their own listener, each as a named client** (ADR 0048). The listener (`ghostd::outside`, `GHOST_MCP_LISTEN`) is a fourth app in `ghostd`: its own addresses, loopback unless the operator set otherwise (logged), one path, no route shared with the control API, the phone listener or the webhook listener, a request with an `Origin` refused, rmcp's `Host` allow-list kept. Every request carries a client's token (`ghost_core::ghost_app::clients`): a password in Ghost's sense, shown once, stored only as its SHA-256, never logged or audited, compared in constant time, five wrong ones lock the name for five minutes, a removed client refused at once. The server names the caller from what the listener authenticated (`client:<name>`), never from an argument, and keeps nothing per connection. A call from outside has no session, so `ghost_app::outside` does the dispatcher's and the gate's part: reads are checked against the `block` rules and logged at debug level only; every other tool goes through the gate's `submit` as `ghost.<tool>` (`block` refuses, `ask` waits on the waiting list and the client is told so, the audit names the client), and each client has a budget. Nothing a client sends is ever the operator's yes, and that holds inside `agent_ask`: the client's text is the instruction of a run with nobody there (`ghostd::outside::AskRunner` over `ghost_voice::headless`; don't write a second runner), so a change at `ask` in it is set aside on the waiting list, the turn is kept in the agent's transcript marked as asked by that tool, and it stops when the client cancels or goes away (a change from outside runs in its own task under `ghost_core::apps::with_cancel`, so the gate is never left with a proposal half made). A schedule a client sets up is made by `client:<name>` and runs as the agent it names; a client manages only its own and reads of the others only that they are there. The documentation and the status are resources for outside clients only, and `tools_search` is not offered to them: in process an advertised resource comes back as two more read tools on every turn (ADR 0046, ADR 0018). To give outside tools something new, add a tool in `ghost_app` with an honest `readOnlyHint`; one only they should have goes in `outside_tools.rs`, so it is not schema on an agent's turn. Never offer them a password (name or value), the policy file, a transcript, audio, or a way to change a permission, an app, a rule, a watch, a prompt or a client: `outside::tests::nothing_an_outside_client_must_not_reach_is_offered` holds that line. Clients are made and removed by the operator only (`ghostd mcp`, `/clients` on the control API), never by a tool.
- **The product says app, never MCP or server** (ADR 0034). The desktop, the phone, the voice, the prompts, tool descriptions, the waiting list and operator docs say *app*, *connect*, *sign in* and *permission*; catalog titles lose the protocol's name. The code keeps `mcp` only where it names the protocol library, and where another tool's own words need it (`ghostd mcp`, `GHOST_MCP_LISTEN`, the `mcpServers` config a tool pastes); the desktop calls those tools *outside tools*.
- **The control API never carries passive audio or passive transcripts, and passwords go in but never come out** (ADR 0013, ADR 0036). The model has no route to it: what a model may read or change of Ghost's own state is the tools of Ghost's own app (ADR 0045), through the gate, and nothing else. That holds for a model in another tool too: the listener for outside tools (ADR 0048) serves Ghost's own app, not the control API, and proxies none of it. A Confirm click in the operator's own desktop session is confirmation evidence, recorded as `classifier: ui`; a confirm from the paired phone (`POST /changes/confirm`) is the gate's confirm by id recorded as `classifier: phone`, evidence only because the request is signed by the paired device (ADR 0051).
- **An answer is the operator's own** (ADR 0051). A question's answer comes from the desktop (route `desktop`), a signed request from the paired phone (`phone`), or the operator's words in a live session (`voice`): `ghost_answer` is offered only to Ghost's own agents, and the session's dispatcher marks it heard (`_heard`) only when its words are in the operator's last turn, the check `rules.add` makes. Never let a model, a run, an outside tool or an app supply or paraphrase an answer, never match a choice with a model (`questions::match_choice` is fixed rules), and never take an answer as a yes to a change: the gate judges that as ever. A question's words are its asker's: shown and said as "Ledger asks: …", data, never Ghost's own. The phone path carries no transcript: a question answered by voice reaches the phone by its choice only, and the live stream carries no turn, log line or audio.
- **Conversations are core** (ADR 0014). `ghost` is conversation zero and every wake lands in it. A conversation's persona, memory and notes are files under `~/.local/share/ghost/conversations/<slug>/` that Ghost writes only through the gate; the transcript and every compaction version are in SQLite. Memory is private per conversation. Persona text shapes the prompt: a thread Ghost creates by voice starts with a short persona Ghost drafts from the conversation (ADR 0019; the operator edits it), but changing a persona by voice stores the operator's words verbatim; never let the model paraphrase those. Session transcripts are stored; passive audio still is not. A run with nobody there (ADR 0047) writes its instruction, calls and answer into the agent's transcript marked `[scheduled run: <name>]` under the run's own session id, shares nothing mutable with a session open beside it, and never opens the microphone or the speaker.
- **Debugging audio goes through `ghost_voice::debug::audio()`**, which is silent unless `GHOST_DEBUG_AUDIO=1`. Do not add ad-hoc transcript logging elsewhere.
- **Passwords live in Ghost's own vault** (ADR 0036, superseding "secrets come from the environment"). *Password* is the operator's word for every API key, token and account password; code keeps `secret`. The vault is one AES-GCM file (`~/.local/share/ghost/passwords.vault`), its key in the keyring through Secret Service (`ghost_core::passwords`); a locked keyring is waited for and put on the waiting list, never a crash. A value goes in and never comes back out: not to the desktop, the control API, a log, the audit, a transcript or the model; the API lists names, what uses each and when it was last used. A password is a name (`${NAME}`) everywhere except its point of use: an app's header or `env`, a webhook's check, Ghost's own settings in the daemon's memory. A stdio app's environment is the one place a value leaves the vault; `child_env()` keeps every password from anything else Ghost starts. Every value is redacted (`redact`, deterministic, 8 characters at least) from app results, errors and descriptions, from what the store writes and from every log line; don't add a path that reads app text or writes a log, the audit or a transcript around it. No plaintext secret file: env files hold non-secret settings only (`settings.env`), heka-vault is a one-time import (`ghostd passwords import`), and nothing renders secrets at start. Never commit a password, and never put one in a prompt or a log line. Tests use a fake keyring (`MemoryKeyring`), never the operator's.
- **Performance is a feature** (ADR 0018, [docs/performance.md](docs/performance.md)). Measure before and after any change made for speed (`make perf`, `make latency`); a change that adds a step to a turn says what it costs; every release runs `make perf` and keeps the report in `docs/benchmarks/perf/`. Speed never overrides the privacy, gate or secrets rules.
- **Ghost's folder is the operator's; there are no departments** (ADR 0035). The model never writes `apps.json`, `watches.json`, `hooks.json`, `policy.toml` or `AGENTS.md` except by appending the operator's words verbatim through the gate (`rules.add`); there is one set of permissions, and don't add a layer that narrows or widens it per agent; a skill never widens anything or runs code outside the gate. Don't bring back departments, a move, or per-department memory, docs or folders: what an agent needs of its own is a field on the agent. Schedules are the one thing the operator owns that is not a file there (ADR 0047): rows in SQLite (`schedules`, with who made each, `operator` or `agent:<slug>`), made by the operator through the control API or by an agent through the gate (`ghost_schedule_manage`, the calling agent taken from the dispatcher, never an argument); an agent manages its own and Ghost manages all. Don't add a `schedules.json`, and don't let a run add a rule, set a permission or write one of those files.
- **The daemon is Rust, one Cargo workspace with the desktop app's shell** (ADR 0039, superseding ADR 0003): `crates/ghostd` and the crates beside it, `cargo` and the one `Cargo.lock`; a known vulnerability or a license outside `deny.toml` fails CI; no Python in the daemon, and no bespoke build of it (`make dev` is `cargo build -p ghostd`, the bundle is `cargo build --release`). The pipeline is Ghost's own (`crates/ghost-voice`): Pipecat's ideas, not its code, and every lesson the Python daemon learned is a test before the stage that embodies it. Python stays for the tools only, each a `uv` project with its lock: `tools/` (the version script, the scripts' tests) and `tools/oracle` (the model wrappers the Rust is measured against, pinned at the versions the parity fixtures were recorded with, the aiortc far end, the wake tooling). The ONNX Runtime the daemon loads is 1.24.4, the one the parity was measured on, fetched once by `scripts/onnxruntime.sh` and shipped in the bundle; don't move to the runtime a crate downloads without rerunning the strict parity suite.

## Commits

Conventional commits. Every change reaches `main` through a pull request: `main` takes no direct pushes, and a PR merges only when the `ci` workflow passes (`.github/workflows/ci.yml`: rustfmt, clippy, nextest and cargo-deny over the workspace, `openapi.json` current from the Rust types and the TS client from it, the bundle, ruff and pytest over the Python tools, typecheck, vitest, the desktop build; the ruleset requires its `ci-ok` job) and the branch is up to date with `main`. Run `make ci` (or `make lint test` and `pnpm typecheck`) before pushing. Don't merge a red PR or ask for a bypass; fix the check. To work on Ghost, `make dev` builds the daemon (`cargo build -p ghostd`) and runs it with the desktop app from the checkout, stopping the service first since only one Ghost may have the microphone (`make reload` after a Rust change rebuilds and restarts the daemon, not the app; `make service-on` to bring the service back). To run a commit as the operator's own Ghost, `make deploy` (`cargo build --release -p ghostd` of HEAD into `~/.local/share/ghost/runtime/<commit>/`, checked with `ghostd check` before the service switches to it, no root; `make deploy-rollback`); never point the service at the working tree.
