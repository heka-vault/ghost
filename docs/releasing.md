# Versions and releases

Ghost's version is a date: `YYYY.M.N`. N counts that month's releases from 0, so the first
release of October 2026 is `2026.10.0` and the next is `2026.10.1`. There are no leading
zeros (`2026.10.0`, never `2026.10.00` or `2026.010.0`), because Cargo, Tauri, npm and Debian
all need an ordinary three-part version. The tag of a release is `v` and the version:
`v2026.10.0`.

## One version, many copies

The root `pyproject.toml` is the source. Every other file that carries a version is a copy
that `scripts/version.py` writes:

- the four member `pyproject.toml` files (`apps/ghostd`, `packages/core`, `packages/voice`,
  `packages/api`) and their five entries in `uv.lock`
- the five `package.json` files (the root, `apps/desktop`, `apps/mobile`,
  `packages/client-ts`, `packages/ui`) and `apps/mobile/app.json`
- the workspace's `Cargo.toml` (inherited by the daemon's crates), `apps/desktop/src-tauri/Cargo.toml`, the shell's entry in the root `Cargo.lock`, and `tauri.conf.json`
- the phone's call module, `apps/mobile/modules/ghost-call/android/build.gradle` (`version`
  and `versionName`); `apps/mobile/android` is generated by `make android` and not committed

The script edits only the version line of each file and leaves the rest of the file as it
was. `apps/ghostd/tests/test_versions.py` reads each copy with its own format's parser and
fails when one disagrees with the root, so CI's pytest catches a copy edited by hand. It also
fails when a `package.json`, `pyproject.toml`, `Cargo.toml` or `build.gradle` is added under `apps/` or
`packages/` and the script doesn't know about it.

```bash
make version                   # the version, any copy that disagrees, and the next release's
make version V=next            # write the next release's version everywhere (fetches tags first)
make version V=2026.11.0       # or a version you name
```

The next release's version comes from today's date and the `v*` tags: one more than the
highest `vYYYY.M.N` tag of this month, or `.0` when this month has none.

## Cutting a release

`main` takes changes only through pull requests that pass CI, so a release has two steps.

1. **Bump the version in a PR.** On a branch, run `make version V=next`, commit (for example
   `chore(release): 2026.10.1`), push and open a PR. CI checks every copy agrees. Merge it
   like any other PR.
2. **Tag it.** On `main`, pulled up to date, run `make release`. It checks that:
   - you are on `main` with no uncommitted changes to tracked files
   - `HEAD` is the same commit as `origin/main` after a fetch, so the tagged commit is the one
     CI passed on `main`
   - every copy agrees with `pyproject.toml`
   - `pyproject.toml`'s version isn't tagged yet and is this month's next release

   Then it makes an annotated tag `vYYYY.M.N` on `HEAD`. **It pushes nothing.** Push the tag
   yourself when you mean it:

   ```bash
   git push origin v2026.10.1
   ```

   The tag starts `.github/workflows/release.yml`. It checks the tag names the version the
   files say, builds the bundle (below), installs the .deb into a clean Ubuntu 26.04 and
   runs `ghostd version`, and attaches the .deb and the AppImage to a GitHub release.

If the month turns between the merge and the tag, `make release` refuses: the merged
`2026.10.x` is no longer this month's. Bump again with `make version V=next` in a PR.

Nothing tags or pushes on its own: no workflow bumps a version or makes a tag.

## The bundle

Ghost ships as one desktop bundle with the daemon inside (ADR 0038): `tauri build` makes a
.deb and an AppImage that carry the app and `ghostd`, built from the same Cargo workspace
(ADR 0039). `make bundle` is `pnpm tauri build`; CI builds it on every push and the release
workflow attaches it.

What `tauri build` does, in order (`apps/desktop/src-tauri/tauri.conf.json`):

1. `scripts/sidecars.sh`: `cargo build --release -p ghostd -p ghost-core --bins`, then the
   three binaries the bundle carries, `ghostd`, `ghost-mock-github` and `ghost-scripts`
   (the two apps `apps.json` names), copied to `apps/desktop/src-tauri/binaries/<name>-<target
   triple>`, where Tauri's bundler looks for `bundle.externalBin`. The folder is not committed.
2. The frontend (`pnpm --filter @ghost/desktop build`).
3. The shell (`cargo build --release` of `heka-ghost-desktop`), then the bundles under
   `target/release/bundle/deb/` and `target/release/bundle/appimage/`. The .deb installs
   the four binaries in `/usr/bin`; the AppImage carries them in its `usr/bin`.

The shell's build script hides `externalBin` from `tauri-build` (the sidecars are the
workspace's own binaries, which `tauri-build` would otherwise copy over cargo's fresh output
in `target/` and demand at every `cargo build`), so a plain `cargo build`, `clippy` or
`nextest` never needs `binaries/`; only the bundler reads it.

The installed app supervises the daemon (ADR 0038): at launch it adopts a daemon already
answering on the control socket, else runs `ghostd restore-volumes` and starts `ghostd run`
in its own process group with `~/.config/ghost/settings.env` (non-secret settings only; a
name in it that looks like a password is left out and named in the app's log), its output
through `systemd-cat -t ghostd` (so `journalctl --user -t ghostd` keeps working) or, with
no journal, `~/.local/state/ghost/ghostd.log` turned over at 10 MB. It starts the daemon
again with backoff (5 s doubling to 60 s) when it exits and says "Ghost restarted". Quit in
the tray sends TERM to the group, waits up to 20 s, then KILL, then `restore-volumes`; the
daemon also stops on its own when the app is gone (`GHOST_PARENT_PID`). The app starts at
login, in the tray with its window hidden (`--hidden`), off from the tray's "Start at login"
(`~/.local/state/ghost/autostart`), and a second launch opens the first one's window. Under `make dev` the app only adopts (`GHOST_SHELL_ADOPT_ONLY=1`), since
`scripts/dev.sh` runs the daemon; `make dev-rust` runs the Rust one the same way.

## What each build says it is

The daemon reports its version and its build in the status the control API returns
(`GET /status`, and the `/events` stream), as `version` and `build: {kind, commit, dirty}`:

| Kind | What it is | Where `build` comes from |
|---|---|---|
| `dev` | Ghost from a checkout (`make dev`, `make daemon`, `uv run ghostd`) | The checkout's `HEAD`, and `dirty` when tracked files had uncommitted changes as the daemon started |
| `deploy` | A `make deploy` runtime in `~/.local/share/ghost/runtime/<commit>/` | `scripts/deploy.sh` writes `venv/ghost-build.json` in the build |
| `release` | The bundle (the .deb or the AppImage) | the Rust daemon, once it reports its build (#39) |

A recorded build is `ghost-build.json` in the venv's root (Python's `sys.prefix`); a venv
without one is a checkout's (`ghostd.build`). The daemon reads it once when it starts: a
file read, or two `git` calls for a checkout, and nothing on a turn. The version is the one
`ghostd` was installed at, which is the root `pyproject.toml`'s.

It reads the same everywhere:

- `ghostd version`: `Ghost 2026.10.0 · dev a1b2c3d` (with `, uncommitted changes` when dirty).
  `ghostd check` and the daemon's first log line start with it, and `make deploy` shows it
  from the build's check.
- The desktop's sidebar footer: `Ghost 2026.10.0 · dev a1b2c3d`. A release shows the version
  alone, since its version is its tag.
- Settings › General: the version, the build in words, and the desktop app's own version.

The desktop app's version is its `package.json`'s, the same as every other copy, and its
commit is the checkout's `HEAD` (and whether tracked files were dirty) when Vite built the
window or started its dev server (`vite.config.ts`, read in `src/app/version.ts`). When the
window and the daemon differ, for example a window from a checkout talking to the deployed
Ghost, the sidebar adds a quiet second line ("This window is 2026.10.1") and General shows a
neutral notice. They differ when the versions do, or, at the same version, when both know
their commits and the commits differ ("This window is 2026.10.1 · e54c2a5"); uncommitted
changes aren't compared. A daemon older than this change has no `build` in its status; the
app shows its version alone.

The restart Settings asks for follows the build: `systemctl --user restart ghostd` for a
deploy or a release; for a `dev` daemon, the make target that started it, which it reports as
`build.launcher` from `GHOST_LAUNCHER` (restarting the service would start a second Ghost
against the microphone): `make reload` under `make dev` or `make daemon` (`make-dev`), `make
restart` under `make start` (`make-start`). The desktop app sets `GHOST_LAUNCHER=desktop` on
the daemon it runs (ADR 0038): that daemon restarts with the app, Quit and open. A checkout
started any other way (a unit running it, `uv run`) has no launcher, and Settings says to
restart Ghost the way it was started.

In the mock (`?mock=passive`), `&build=dev|dirty|start|checkout|deploy|release|behind` sets
what the daemon says it is: `dev`, `dirty`, `start` and `checkout` are at this window's own
commit (`start` is `make start`'s, `checkout` has no launcher); `deploy` and `release` are
this window's version at another commit, so the notice shows the builds differ; `behind` is
last month's deploy, so the notice shows the versions differ.

## Which daemon `make deploy` runs

Until W10 of #39 removes the Python daemon, a `make deploy` build carries both: the venv
(`venv/bin/ghostd`) and the Rust daemon (`cargo build --release -p ghostd` from the archived
tree, as `bin/ghostd`; the target dir `~/.local/share/ghost/runtime/.cargo-target` is shared
across builds so a deploy only compiles what changed). `make deploy IMPL=rust` or
`IMPL=python` says which one the service runs; a build records the choice in `daemon-impl`
(python when it never said), and the drop-in carries it as `Environment=GHOST_DAEMON_IMPL=`
with the matching `ExecStart` and `ExecStopPost`. A rollback runs what the earlier build
recorded. `ghostd check` is the Python daemon's until the Rust one has it; a Rust deploy
prints the daemon's version from the build instead.

## Rolling back across the vault

`make deploy-rollback` switches the service back to the build that ran before, and writes the
systemd drop-in that build needs, not the one the current checkout writes. Each build records
its form in `~/.local/share/ghost/runtime/<commit>/dropin-form` (`scripts/deploy.sh dropin
[commit]` prints the drop-in a build runs with):

- `vault`: the environment is `settings.env` only and the daemon opens Ghost's vault itself
  (ADR 0036). Every build `make deploy` makes from now on.
- `render`: a build from before the vault. Its own `src/infra/systemd/ghost-render-env.sh`
  runs as `ExecStartPre`, and the daemon reads its passwords from `~/.config/ghost/env`
  (`EnvironmentFile=-%h/.config/ghost/env`, optional so the renderer runs first when the
  file is gone).

A build with no record is a `render` build when its tree still has `ghost-render-env.sh`, and a
`vault` build otherwise.

The vault's import deletes `~/.config/ghost/env`. A pre-vault build's renderer writes it again
from heka-vault while heka-vault's config (`~/.config/heka-vault/ghost.env`) is on this
computer, so a rollback then goes ahead. Without either file the build would start with no
passwords: the rollback refuses, says so, and changes nothing; stay on the vault build, or
write the passwords back into `~/.config/ghost/env` by hand first.

`scripts/deploy.sh off` removes the drop-in and hands the service back to
its unit file. A unit installed before the vault runs `infra/systemd/ghost-render-env.sh`,
which is gone, and reads `~/.config/ghost/env`; `off` refuses that unit and keeps the drop-in.
A pre-step marked `ExecStartPre=-…` doesn't count: systemd starts the unit when it fails.
`make service-install` installs the current unit, then `off` works.
