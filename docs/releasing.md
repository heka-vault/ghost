# Versions and releases

Ghost's version is a date: `YYYY.M.N`. N counts that month's releases from 0, so the first
release of October 2026 is `2026.10.0` and the next is `2026.10.1`. There are no leading
zeros (`2026.10.0`, never `2026.10.00` or `2026.010.0`), because Cargo, Tauri, npm and Debian
all need an ordinary three-part version. The tag of a release is `v` and the version:
`v2026.10.0`.

## One version, many copies

The root `pyproject.toml` is the source (it carries the version, the ruff settings and the
tools' uv workspace; the daemon is Rust, ADR 0039). Every other file that carries a version
is a copy that `tools/version.py` writes:

- the tools' `pyproject.toml` files (`tools/`, `tools/oracle`), their entries in `uv.lock`
  (`ghost`, `ghost-tools`) and `tools/oracle/uv.lock` (`ghost-oracle`)
- the five `package.json` files (the root, `apps/desktop`, `apps/mobile`,
  `packages/client-ts`, `packages/ui`) and `apps/mobile/app.json`
- the workspace's `Cargo.toml` (inherited by the daemon's crates), `apps/desktop/src-tauri/Cargo.toml`, the shell's entry in the root `Cargo.lock`, and `tauri.conf.json`
- the phone's call module, `apps/mobile/modules/ghost-call/android/build.gradle` (`version`
  and `versionName`); `apps/mobile/android` is generated by `make android` and not committed

The script edits only the version line of each file and leaves the rest of the file as it
was. `tools/tests/test_versions.py` reads each copy with its own format's parser and
fails when one disagrees with the root, so CI's pytest catches a copy edited by hand. It also
fails when a `package.json`, `pyproject.toml`, `Cargo.toml` or `build.gradle` is added under `apps/`,
`packages/` or `tools/` and the script doesn't know about it.

```bash
make version                   # the version, any copy that disagrees, and the next release's
make version V=next            # write the next release's version everywhere (fetches tags first)
make version V=2026.11.0       # or a version you name
```

The next release's version comes from today's date and the `v*` tags: one more than the
highest `vYYYY.M.N` tag of this month, or `.0` when this month has none.

## Cutting a release

`main` takes changes only through pull requests that pass CI, so a release has two steps.

1. **Bump the version in a PR.** On a branch, run `make version V=next`, commit (for example
   `chore(release): 2026.10.1`), push and open a PR. CI checks every copy agrees. Merge it
   like any other PR.
2. **Tag it.** On `main`, pulled up to date, run `make release`. It checks that:
   - you are on `main` with no uncommitted changes to tracked files
   - `HEAD` is the same commit as `origin/main` after a fetch, so the tagged commit is the one
     CI passed on `main`
   - every copy agrees with `pyproject.toml`
   - `pyproject.toml`'s version isn't tagged yet and is this month's next release

   Then it makes an annotated tag `vYYYY.M.N` on `HEAD`. **It pushes nothing.** Push the tag
   yourself when you mean it:

   ```bash
   git push origin v2026.10.1
   ```

   The tag starts `.github/workflows/release.yml`. It checks the tag names the version the
   files say, builds the bundle (below), installs the .deb into a clean Ubuntu 26.04 and
   runs `ghostd version`, and attaches the .deb and the AppImage to a GitHub release.

If the month turns between the merge and the tag, `make release` refuses: the merged
`2026.10.x` is no longer this month's. Bump again with `make version V=next` in a PR.

Nothing tags or pushes on its own: no workflow bumps a version or makes a tag.

## The bundle

Ghost ships as one desktop bundle with the daemon inside (ADR 0038): `tauri build` makes a
.deb and an AppImage that carry the app and `ghostd`, built from the same Cargo workspace
(ADR 0039). `make bundle` is `pnpm tauri build`; CI builds it on every push and the release
workflow attaches it.

What `tauri build` does, in order (`apps/desktop/src-tauri/tauri.conf.json`):

1. `scripts/sidecars.sh`: first `scripts/onnxruntime.sh stage`, which fetches ONNX Runtime
   1.24.4 once (Microsoft's release archive, pinned by SHA-256, into
   `~/.cache/ghost/onnxruntime/1.24.4/`) and copies the library and its license to
   `apps/desktop/src-tauri/resources/onnxruntime/`; then `scripts/models.sh stage`, which
   fetches the four small model files once (each from its upstream release, pinned by
   SHA-256 to the bytes the Python wheels shipped, into `~/.cache/ghost/models/`; [the
   speech models](#the-speech-models)) and copies them with their licences to
   `apps/desktop/src-tauri/resources/models/`; then `cargo build --release -p ghostd
   -p ghost-core --bins` and the three binaries the bundle carries, `ghostd`,
   `ghost-mock-github` and `ghost-scripts` (the two apps `apps.json` names), copied to
   `apps/desktop/src-tauri/binaries/<name>-<target triple>`, where Tauri's bundler looks for
   `bundle.externalBin`. Neither folder is committed.
2. The frontend (`pnpm --filter @ghost/desktop build`).
3. The shell (`cargo build --release` of `heka-ghost-desktop`), then the bundles under
   `target/release/bundle/deb/` and `target/release/bundle/appimage/`. The .deb installs
   the four binaries in `/usr/bin`, the runtime's library in
   `/usr/lib/heka-ghost-desktop/onnxruntime/libonnxruntime.so.1.24.4` and the model files
   in `/usr/lib/heka-ghost-desktop/models/` (`bundle.resources`); the AppImage carries them
   in its `usr/bin` and `usr/lib`. The .deb depends on
   `libespeak-ng1` (Kokoro's phonemizer; the one system library `ghostd` links that a bare
   Ubuntu lacks) on top of the GTK and WebKit packages Tauri adds.

The shell's build script hides `externalBin` and `resources` from `tauri-build` (the
sidecars are the workspace's own binaries, which `tauri-build` would otherwise copy over
cargo's fresh output in `target/` and demand at every `cargo build`, and it would demand
the staged library the same way), so a plain `cargo build`, `clippy` or `nextest` never
needs `binaries/` or `resources/`; only the bundler reads them.

ONNX Runtime is loaded at run time, not linked (`ort` with `load-dynamic`): the one Ghost
runs is 1.24.4, the build the Python daemon ran, on which every model is bit-exact with
the oracle (`crates/ghost-infer/tests/parity.rs`); the crate's own download, 1.31.0, moves
the int8 kernels and the vocoder. `ghostd` looks for the library in `ORT_DYLIB_PATH`, then
beside itself in the bundle (`/usr/bin/ghostd` finds `/usr/lib/heka-ghost-desktop/onnxruntime/`),
then in the cache (`crates/ghost-infer/src/runtime.rs`); `ghostd check` prints the one it
would load. The four small model files are found the same way (`GHOST_MODELS_DIR`, the
bundle's `models/`, `~/.cache/ghost/models/`; `crates/ghost-infer/src/models.rs`). CI runs
`scripts/onnxruntime.sh` and `scripts/models.sh` before `cargo nextest`, since every test
that opens a session needs the library and the daemon the parent-death tests start reads
Silero, and the release workflow's install test runs `ghostd check` in a clean container,
where the daemon must find the bundle's copies on its own.

The installed app supervises the daemon (ADR 0038): at launch it adopts a daemon already
answering on the control socket, else runs `ghostd restore-volumes` and starts `ghostd run`
in its own process group with `~/.config/ghost/settings.env` (non-secret settings only; a
name in it that looks like a password is left out and named in the app's log), its output
through `systemd-cat -t ghostd` (so `journalctl --user -t ghostd` keeps working) or, with
no journal, `~/.local/state/ghost/ghostd.log` turned over at 10 MB. It starts the daemon
again with backoff (5 s doubling to 60 s) when it exits and says "Ghost restarted". Quit in
the tray sends TERM to the group, waits up to 20 s, then KILL, then `restore-volumes`; the
daemon also stops on its own when the app is gone (`GHOST_PARENT_PID`). The app starts at
login, in the tray with its window hidden (`--hidden`), off from the tray's "Start at login"
(`~/.local/state/ghost/autostart`), and a second launch opens the first one's window. Under `make dev` the app only adopts (`GHOST_SHELL_ADOPT_ONLY=1`), since
`scripts/dev.sh` runs the daemon.

## The speech models

Four small model files are in the bundle, and the daemon finds them on its own; the three
large ones are not, and each gets to its place by a step run once on the machine.

| Model | Where `ghostd` reads it | How it gets there |
|---|---|---|
| Silero VAD (`silero_vad.onnx`), Smart Turn v3.2 (`smart-turn-v3.2-cpu.onnx`) and the wake front end (`melspectrogram.onnx`, `embedding_model.onnx`) | `GHOST_MODELS_DIR`, else the bundle's `/usr/lib/heka-ghost-desktop/models/`, else `~/.cache/ghost/models/` (`crates/ghost-infer/src/models.rs`; `GHOST_SILERO_MODEL` and `GHOST_SMART_TURN_MODEL` name a file of their own) | `scripts/models.sh` (`make models`; `make setup`, `make dev` and CI run it): each from its upstream release, pinned by SHA-256 to the bytes the Python wheels shipped (pipecat-ai 1.12.0, livekit-wakeword 0.3.0; every upstream file matched its wheel's on 2026-10-29). Silero from snakers4/silero-vad at v6.0 (MIT), Smart Turn from the pipecat-ai/smart-turn-v3 Hugging Face repository at `f766f81` (BSD-2-Clause), the two graphs from dscripka/openWakeWord's v0.5.1 release (Apache-2.0), each licence beside its file. `stage` copies them into the bundle; a file that doesn't match its pin is refused with both hashes printed |
| Parakeet TDT 0.6B v3, int8 (ADR 0004) | `GHOST_STT_DIR`, else the Hugging Face cache, `~/.cache/huggingface/hub/models--istupakov--parakeet-tdt-0.6b-v3-onnx/` | `onnx_asr` in the oracle fetches it on first use (about 700 MB): `uv run --project tools/oracle python -I -c "import onnx_asr; onnx_asr.load_model('nemo-parakeet-tdt-0.6b-v3', quantization='int8')"` |
| Kokoro v1.0 (ADR 0004) | `GHOST_TTS_MODEL_PATH` and `GHOST_TTS_VOICES_PATH`, else `~/.cache/ghost/kokoro/kokoro-v1.0.onnx` and `voices-v1.0.bin` | The two files of the `model-files-v1.0` release of thewh1teagle/kokoro-onnx, which the Python daemon fetched through Pipecat (about 340 MB together): `curl -fL --create-dirs -o ~/.cache/ghost/kokoro/kokoro-v1.0.onnx https://github.com/thewh1teagle/kokoro-onnx/releases/download/model-files-v1.0/kokoro-v1.0.onnx`, and the same URL and path with `voices-v1.0.bin` |
| The trained wake classifiers (ADR 0025, `GHOST_WAKE_MODE=onnx`) | `GHOST_WAKE_MODEL_PATH`, else `~/.cache/ghost/wake/hey_ghost.onnx`, and every `ghost_*.onnx` beside it for Ghost by name | The operator's own, trained and copied there as [wake-recording.md](wake-recording.md) says; nothing fetches them |

`ghostd check` prints the folder of each it finds (`models:`, `parakeet:`, `kokoro:`, and
`wake models:` in onnx wake mode) and, for one that is missing, names the script or the step
above as a problem; nothing panics for a missing file, and a daemon started without one
says so and exits (or, for a classifier, listens by transcript instead). The parity suite
reads the same files (`crates/ghost-infer/tests/parity.rs`).

## What each build says it is

The daemon reports its version and its build in the status the control API returns
(`GET /status`, and the `/events` stream), as `version` and `build: {kind, commit, dirty}`:

| Kind | What it is | Where `build` comes from |
|---|---|---|
| `dev` | Ghost from a checkout (`make dev`, `make daemon`, `cargo run -p ghostd`) | The checkout's `HEAD`, and `dirty` when tracked files had uncommitted changes as the daemon started |
| `deploy` | A `make deploy` runtime in `~/.local/share/ghost/runtime/<commit>/` | `scripts/deploy.sh` writes `bin/ghost-build.json` beside the binary |
| `release` | The bundle (the .deb or the AppImage) | Not recorded yet: the bundle's daemon says `dev` with no commit, since nothing beside `/usr/bin/ghostd` is written at build time (open) |

A recorded build is `ghost-build.json` beside the executable; a binary without one is a
checkout's (`ghostd::build_info`). The daemon reads it once when it starts: a file read, or
two `git` calls for a checkout, and nothing on a turn. The version is the one the crate was
built with (`Cargo.toml`'s `[workspace.package]`, a copy of the root `pyproject.toml`'s).

It reads the same everywhere:

- `ghostd version`: `Ghost 2026.10.0 · dev a1b2c3d` (with `, uncommitted changes` when dirty).
  `ghostd check` and the daemon's first log line start with it, and `make deploy` shows it
  from the build's check.
- The desktop's sidebar footer: `Ghost 2026.10.0 · dev a1b2c3d`. A release shows the version
  alone, since its version is its tag.
- Settings › General: the version, the build in words, and the desktop app's own version.

The desktop app's version is its `package.json`'s, the same as every other copy, and its
commit is the checkout's `HEAD` (and whether tracked files were dirty) when Vite built the
window or started its dev server (`vite.config.ts`, read in `src/app/version.ts`). When the
window and the daemon differ, for example a window from a checkout talking to the deployed
Ghost, the sidebar adds a quiet second line ("This window is 2026.10.1") and General shows a
neutral notice. They differ when the versions do, or, at the same version, when both know
their commits and the commits differ ("This window is 2026.10.1 · e54c2a5"); uncommitted
changes aren't compared. A daemon older than this change has no `build` in its status; the
app shows its version alone.

The restart Settings asks for follows the build: `systemctl --user restart ghostd` for a
deploy or a release; for a `dev` daemon, the make target that started it, which it reports as
`build.launcher` from `GHOST_LAUNCHER` (restarting the service would start a second Ghost
against the microphone): `make reload` under `make dev` or `make daemon` (`make-dev`), `make
restart` under `make start` (`make-start`). The desktop app sets `GHOST_LAUNCHER=desktop` on
the daemon it runs (ADR 0038): that daemon restarts with the app, Quit and open. A checkout
started any other way (a unit running it, `cargo run`) has no launcher, and Settings says to
restart Ghost the way it was started.

In the mock (`?mock=passive`), `&build=dev|dirty|start|checkout|deploy|release|behind` sets
what the daemon says it is: `dev`, `dirty`, `start` and `checkout` are at this window's own
commit (`start` is `make start`'s, `checkout` has no launcher); `deploy` and `release` are
this window's version at another commit, so the notice shows the builds differ; `behind` is
last month's deploy, so the notice shows the versions differ.

## What `make deploy` builds

A `make deploy` build is the commit's files (`git archive`) and the daemon compiled from them
(`cargo build --release -p ghostd` from the archived tree, as `bin/ghostd`; the target dir
`~/.local/share/ghost/runtime/.cargo-target` is shared across builds so a deploy only
compiles what changed), with the ONNX Runtime library copied from the cache beside it as
`lib/libonnxruntime.so.1.24.4` when the tree has `scripts/onnxruntime.sh`. The build is
checked with its own `ghostd check` against `~/.config/ghost` before the service switches to
it. The drop-in (`scripts/deploy.sh dropin [commit]` prints it) runs `current/bin/ghostd`
with `settings.env` only, since the daemon opens Ghost's vault itself (ADR 0036), and names
the build's library as `ORT_DYLIB_PATH` when it carries one.

## Rolling back

`make deploy-rollback` switches the service back to the build that ran before and rewrites
the drop-in for it. A build from before the Rust daemon (a venv and no `bin/ghostd`) can't
run any more: the rollback refuses, says so, and changes nothing. Every such build is also
from before the vault, so the drop-in's older form, which rendered `~/.config/ghost/env` from
heka-vault, went with it.

`scripts/deploy.sh off` removes the drop-in and hands the service back to
its unit file. A unit installed before the vault runs `infra/systemd/ghost-render-env.sh`,
which is gone, and reads `~/.config/ghost/env`; `off` refuses that unit and keeps the drop-in.
A pre-step marked `ExecStartPre=-…` doesn't count: systemd starts the unit when it fails.
`make service-install` installs the current unit, then `off` works.
