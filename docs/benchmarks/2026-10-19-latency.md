# Where a Ghost turn's time goes

2026-10-19, the workstation (12 CPUs, load about 1.2 from two passive `ghostd` instances).
Tools: the per-turn timeline and the harness in [latency-harness.md](latency-harness.md). Raw
data stays local in `.scratch/perf/2026-10-19/` (records, reports, logs).

Model endpoint: `ANTHROPIC_BASE_URL` pointed at an Anthropic-compatible proxy on the
operator's LAN (`GHOST_LLM_ENDPOINT=proxy`). Its `/v1/models` answers
in 5-9 ms, so the network to it is not the cost; what it does upstream is. There is no
direct Anthropic key on this machine; OpenRouter's Anthropic Messages API
(`https://openrouter.ai/api`, `OPENROUTER_API_KEY`) is the second path for the same models.

## Headline

Baseline: every scenario, 3 runs, Ghost's configuration (Sonnet 5.5, `between_tools`,
the proxy). 45 voice turns, operator stops talking to Ghost's voice:

| | p50 | p95 | mean |
|---|---|---|---|
| reply | 5.00 s | 13.39 s | 6.46 s |
| hear (VAD silence, STT, Smart Turn, hold) | 1.16 s | 1.22 s | |
| model, all calls on the path | 3.60 s | 11.47 s | 5.03 s (78%) |
| TTS to first audio and out | 0.46 s | 3.43 s | 1.00 s (15%) |
| tools (mock GitHub) | 0.01 s | 0.02 s | |

Per scenario, reply p50: hello 3.3 s, small talk 2.9 s, lookup 8.3 s, two-tool chain
16.0 s (p95 23.8 s), approve 6.2 s, "close infra 17" 5.3 s, a hedge that needs a yes 9.1 s,
goodbye shortcut 0.72 s, goodbye through the model 3.6 s. The greeting starts 0.36 s after
the session is built (p50).

## Top contributors

1. **Model calls: 3.6 s p50, 78% of a turn.** Each call is 1.1-2.0 s to first byte at p50
   through the proxy, and a tool turn makes two or three in sequence. The proxy has bad
   minutes: in the baseline window 13 of 79 calls (16%) took over 3 s to first byte, up to
   9.9 s; fifteen minutes later the same calls ran p50 1.22 s, p95 1.96 s.
   - With `between_tools`, Sonnet 5.5's text arrives all at once (60-75 output tokens
     within 0.04 s of the first byte, on both endpoints), so first byte is effectively the
     whole reply. With `adaptive` the hello streamed and its first text came at 0.67 s
     instead of 1.31 s (OpenRouter, n=3).
   - **Narration before a tool call costs about 1 s.** 15 of 42 model turns wrote text
     before calling a tool. `NarrationCut` keeps it from being spoken, but writing it
     delayed the call: first text to tool call p50 0.99 s, against 0.23 s from first byte
     to tool call when there was no text.
   - **Independent lookups run one after another.** The chain question ("what's going on
     with app 142, and what have people said") made get_issue and list_comments in
     separate model calls in all 3 runs; no turn in the baseline used parallel tool calls.
     That is one extra 1.3-3 s round trip.
2. **TTS: Kokoro renders the whole first sentence before any audio.** 0.23 s per second of
   speech: 3 words 0.30 s, 8 words 0.61 s, 15 words 1.12 s, 30 words 2.42 s
   (`kokoro.create_stream` yields one chunk per sentence). Short answers are fine (0.42 s
   p50), but a list answer opens with a long sentence: 10 of 45 turns spent over 1 s, 8
   over 2 s, up to 3.5 s.
3. **The grace hold: 0.80 s on every voice turn** (11-17% of the turn), on top of Smart
   Turn, which said "complete" with p 0.97-0.99 on every one of 51 verdicts. The hold
   kept a turn together when a comma pause split it (6 of 45 turns), but a 0.7 s pause
   mid-sentence still split the turn in 3 of 3 runs: the first half went to the model
   and was interrupted, and the answer came after the second half (lookup_pause 11.1 s
   against lookup 8.3 s).
4. **VAD stop silence: 0.20 s** (`GHOST_VAD_STOP_SECS`), the floor before anything can happen.
5. **STT: 0.16 s p50** (Parakeet: 0.10 s for one word, 0.14 s for 9 words, 0.26 s for 22).

Small: Smart Turn 0.01 s on the path (0.06 s inference); Jev confirmation 0.24 s
(classify) on the `confirm_yes` answer, p50 0.16 s and p95 0.31 s standalone, never past its 0.5 s deadline
(0 of 28); interceptors under 1 ms; pipeline hops 0.02 s; tools on the mock 5-15 ms
(the gate's submit 10 ms, the ADR 0017 request check 4 ms). The mock hides GitHub: a real
read or write adds an API round trip per call, plus snapshot, apply and readback for a
write.

## Prompt caching

`enable_prompt_caching=True` works within a session: Pipecat marks the last two user
messages, and the second call of a turn reads everything but the new tool result (lookup:
read 3,037, write 297). Share of input tokens read from cache in the baseline: 66% on
one-call turns, 85-96% on tool turns and longer sessions.

**Across sessions nothing before the first user message is reused.** On OpenRouter the
first call of every session read 0 and wrote about 3,040 tokens (tool schemas, system
prompt, the first line), 20 sessions out of 20, minutes apart and inside the 5-minute TTL.
The prefix is byte-identical across sessions; there is just no breakpoint at its end, so
nothing is written there to read back. Through the proxy the first call reads 2,177 and
writes about 1,110: the proxy adds a breakpoint of its own over its injected prefix and the
tool schemas, but Ghost's system prompt is still written every session. With a
`cache_control` marker on the system prompt (benchmark variant `+sysbp`) later sessions
read the whole prefix and wrote nothing.

What it buys: little time at this size (Sonnet first call 1.51 s mean vs 1.42 s for later
calls on OpenRouter; 1.69 s vs 1.64 s p50 through the proxy) and about 10x less input cost
on each session's first call. Nothing in the prefix changes per turn: the system prompt is
fixed per conversation, the tool list is fixed per session, thinking is pinned, and the
conversation record (`RECENT_TEMPLATE`) is the first user message, so it is only ever
written once per session. Sonnet 5.5 keeps earlier-turn thinking blocks, so they don't
break the cache. Minimum cacheable prefix on Sonnet 5.5 and Haiku 5.5 is 512 tokens; Ghost's
is about 2.2-3k.

## Thinking mode

(Superseded by the interleaved test under [After the changes](#after-the-changes):
`between_tools` stays.) Sonnet 5.5 through the proxy, small talk, lookup, chain and the hedge-then-yes, 2 runs each
(10 voice turns per mode, run one mode after the other):

| thinking | reply p50 / p95 | model p50 | TTFB p50 | calls with thinking | narrated tool calls |
|---|---|---|---|---|---|
| `between_tools` (Ghost's) | 8.88 / 13.17 | 6.07 | 1.59 | 0/22 | 7 |
| `adaptive` (effort default) | 7.68 / 15.21 | 4.88 | 1.46 | 6/22 | 0 |

Adaptive thought on a quarter of the calls and never narrated before a tool; it wasn't
slower here. Through the proxy both modes arrive unstreamed. On OpenRouter (3 rounds) adaptive
streamed the hello, first text at 0.67 s against 1.31 s. This is a lead, not a result: the
proxy's spread is larger than the difference. It needs an interleaved run on a steady
endpoint, and `effort` set explicitly.

## Desk and phone

Small talk, lookup and approve, 3 runs each, through the scripted desk devices and through
`SmallWebRTCTransport` with an aiortc peer on loopback (Opus both ways, thinking sound off).
The server-side stages are the same (hear 1.17 s, STT 0.17 s, greeting 0.31 s desk vs 0.35 s
from the peer connecting). What differs is outside the pipeline: `audible`, the operator's
last frame to Ghost's voice at the speaker or the peer, lands 0.14 s before the live
`reply` on the desk (the VAD dates the end of speech a little before the line's last
frame) and 0.11 s after it on the phone. **WebRTC adds about 0.25 s (p50) on loopback**,
uplink and downlink together, Opus framing and both jitter buffers. A real phone on Wi-Fi
adds its network round trip and Android's jitter buffer on top. The live log's `reply` for
a phone turn starts at the desk's VAD, so it under-reports what the operator hears by at
least that much.

## Turn hold

`GHOST_TURN_GRACE_SECS`, 3 runs each of small talk and the lookup with a 0.7 s pause
mid-sentence ("What needs my sign-off ... in the app repo?"):

| hold | hear p50 | small talk reply p50 | 0.7 s pause |
|---|---|---|---|
| 0.4 s | 0.74-0.78 s | 2.46 s | split 3/3: a model call started and was interrupted |
| 0.8 s (default) | 1.16-1.18 s | 2.92 s | split 3/3 |
| 1.2 s | 1.55-1.57 s | 3.46 s | kept whole 3/3 |

Every second of hold is a second on every turn, and at 0.8 s it doesn't cover a 0.7 s
pause: the VAD needs its 0.2 s `start_secs` of speech, plus the onset, before the hold
hears that the operator went on. The pauses it does save are the short ones inside a
sentence (a comma: 6 of 45 baseline turns, all kept whole). Smart Turn was confident on
every verdict (p 0.97-0.99, 0 of 51 incomplete), so its own 3 s silence timeout never cost
anything here. These are synthetic voices; the operator's real pauses are the number to
tune against, and the live records now carry `segments` and `kept_open` per turn.

## Recommendations, by expected gain

Gains are per voice turn against the baseline (reply p50 5.0 s, mean 6.5 s, p95 13.4 s).
The operator approved 1, 2, 3, 5 (as a test) and 6-7; the results are in
[After the changes](#after-the-changes) below. 4, hiding the hold, is still open.

1. **Take the voice path off the shared proxy's tail.** Expected: p95 down by 1-5 s, p50 by
   0-0.4 s a call. The proxy's median is fine, but in two of the windows measured today
   (13:58-14:12 and 14:36-14:40) it ran 3-10 s to first byte on many calls. OpenRouter's
   Anthropic API, interleaved with it, had about half the p95 for the same model (hello
   2.5 s vs 4.3 s). A dedicated
   key for Ghost is already an open item in the architecture doc. At Ghost's mostly-cached
   prompt, Sonnet on OpenRouter costs well under a cent a turn.
2. **Fewer model round trips on tool turns.** Expected: 1-3 s on lookups that need more than
   one read, 0.8 s whenever the model narrates. Options: a read tool that returns an issue
   with its latest comments (one call for "what's going on with X"); a prompt line asking
   for independent lookups in one response (Pipecat already runs parallel calls
   concurrently); and the narration fix in 5.
3. **Start speaking after the first clause, not the first sentence.** Expected: TTS p95
   3.4 s down to about 0.6 s, mean about 0.5 s lower; 2-3 s on list answers. Kokoro renders a
   whole sentence before any audio (0.23 s per second of speech). A text aggregator on
   `KokoroTTS` that releases the first chunk at a comma, colon or dash after a few words, and
   sentences after that, would do it; a prompt line ("lead with a short sentence") helps
   too. This also makes a faster model pay off: Haiku's model savings went into longer
   first sentences.
4. **Hide the grace hold behind the first model call.** Expected: up to 0.8 s on every
   voice turn. At Smart Turn's verdict, start the model on a provisional context and hold
   its response until the hold ends; drop it if the operator goes on. Pipecat 1.12 has the
   parts (`UserTurnSpeculation`, `SpeculationGate`). Ghost-specific catch: a speculative
   response must not execute `change`, `switch_conversation` or `go_to_sleep` before the
   turn commits, since the gate holds frames, not tool execution. With that in place the
   hold could grow to 1.2 s, which kept a 0.7 s pause whole, at no cost while the model
   call is longer than the hold. The cheap version: 0.4 s saves 0.4 s a turn now, but splits
   more pauses.
5. **Try `adaptive` thinking against `between_tools`, properly.** Expected: up to 0.8 s on
   tool turns (no narration) and earlier first text, if it holds up in an interleaved run
   with `effort` pinned. Today's numbers point that way but are within the proxy's noise.
6. **Cache the static prefix across sessions.** Expected: about 0.1 s on a session's first
   call, and about 10x less input cost for it. Put a `cache_control` marker on the system
   prompt (Pipecat marks only the last two user messages, and 2 of the 4 breakpoints are
   free), and optionally send a `max_tokens: 0` pre-warm at wake, while the greeting plays.
7. **Small:** `build_session` makes a new `AsyncAnthropic` client per session, so an HTTPS
   endpoint pays a TLS handshake on each session's first call (tens of ms); one client per
   process avoids it. The phone's extra 0.25 s is WebRTC's own and isn't in the live phone
   number; worth knowing before tuning it.

Not worth chasing now: STT (0.16 s), VAD silence (0.20 s, the floor), Smart Turn (0.01 s on
the path), Jev (0.24 s, and only on a yes), the gate and tools on the mock (under 20 ms).
Real GitHub calls will add an API round trip per read and three for a write (snapshot,
apply, readback). The harness can measure them once a PAT is in place.

## After the changes

Same afternoon, same harness, every comparison interleaved (each config runs a scenario
before any runs it again). Raw data in `.scratch/perf/2026-10-19b/`.

What changed:

- **Endpoint setting.** `GHOST_LLM_ENDPOINT=proxy|openrouter` (default `proxy`, as before).
  `openrouter` uses `https://openrouter.ai/api` with `OPENROUTER_API_KEY` from the
  environment and maps `GHOST_LLM_MODEL` to OpenRouter's id (`claude-sonnet-5-5` is
  `anthropic/claude-sonnet-5.5`). `ghostd check` and the daemon's startup log say which
  endpoint and model are in use, never a key (`ghost_voice.config`).
- **Clause TTS.** Kokoro gets text at a comma, colon, semicolon or dash after 4 words, as
  well as at a sentence end (`ghost_voice.clauses`, `GHOST_TTS_CLAUSES`,
  `GHOST_TTS_CLAUSE_MIN_WORDS`). `NarrationCut` still holds a short reply until the response
  ends; the released reply then reaches Kokoro clause by clause. The tap, the echo filter
  and the context still see whole replies.
- **get_issue brings its latest 3 comments** (fetched alongside the issue, so no extra round
  trip to GitHub; `GHOST_GITHUB_ISSUES_ISSUE_COMMENTS`, 0 for the old behaviour), and the
  tool descriptions and the ability's prompt say so.
- **Two prompt lines:** open with a few words that answer, then the detail; ask for
  independent lookups together in one response.
- **A cache marker on the system prompt** (`ghost_voice.llm.GhostAnthropicLLMService`), the
  third of four breakpoints.
- **One `AsyncAnthropic` per process** (per endpoint, key and event loop) instead of one per
  session.

### Cache

Verified on OpenRouter: with the marker, the first call of a session read the whole prefix
when another session had run in the last 5 minutes, **19 of 20 sessions, median 3,105
tokens read and 90 written**. Before, 0 of 20, about 3,040 written each time. The one
miss was the very first session after the change. It buys cost, not time: with the marker
off (but interleaved with variants that wrote the same prefix, so it still read), TTFB was
the same. Through the proxy the marker doesn't stop the write: its first calls still wrote
about 1,220 tokens, so the proxy appears to reshape the system prompt.

**Pre-warm:** not added. A `max_tokens: 0` request with Ghost's prompt and tools works on
OpenRouter (1.2 s), and a first call after it was 1.01 s p50 against 1.13 s cold, but the
per-round difference was 0.03 s at the median (8 paired rounds, the mean pulled by two),
which isn't worth a second request per session and its own failure path.

**One client per process:** 0.09-0.12 s on a session's first call on OpenRouter (a new
client 1.11 s p50 against the shared one 1.02 s, paired median 0.115 s, 8 rounds): the TLS
handshake it no longer repeats.

### Thinking: `between_tools` stays

OpenRouter, the new Ghost, every scenario that uses the model, 3 runs each, interleaved
(42 and 39 voice turns):

| | `between_tools` (kept) | `adaptive` |
|---|---|---|
| reply p50 / p95 | 4.28 / 6.56 | 3.90 / 7.15 |
| model time p50 | 2.65 | 2.21 |
| first content block p50 / p95 | 1.18 / 1.43 | 0.81 / 2.31 |
| tool calls with text before them | 15/31 | 0/30 |
| goodbye through the model spoken | 3/3 | **0/3** |
| other drift (wrong tool or change) | 0/27 runs | 0/27 runs |

Adaptive is 0.4 s faster at the median (the comments question 4.74 s against 5.54 s, approve
3.96 s against 4.64 s) but has a longer tail (the hedge-then-yes 8.85 s against 7.15 s at
p95), and it breaks the model's goodbye. Sonnet 5.5 returns text written before a tool call
as a hidden progress-update thinking block in adaptive mode, so "we can stop here" got a
go_to_sleep with its goodbye (about 54 tokens) never spoken: Ghost hung up in silence 3 times
out of 3. The same mechanism is why nothing counted as narration: the text is still
written, just hidden, and its first block arrives sooner. Not at least as good, so the
default stays. The harness now flags a silent hang-up.

The greeting regression above was noise: in this run the new Ghost greeted at 2.92 s p50
(model 1.41 s), against 2.75 s for the old one on the same endpoint earlier.

### Still worth doing

1. **Hide the grace hold behind the first model call** (recommendation 4 above). The hold is
   now the largest fixed cost: hearing is 1.07 s of a 4.0 s mean reply, 0.8 s of it the hold.
2. **Give go_to_sleep its goodbye as an argument** that Ghost speaks itself. It makes the
   goodbye independent of how the model's text is returned, and would let adaptive thinking
   (0.4 s at the median) be tried again.
3. **Narration still happens on about half the tool calls** with `between_tools` (13/20,
   15/31), about 0.8 s each. A stronger prompt or the change in 2 then adaptive.
4. **Long first clauses.** On the comments question the reply often opens with a 12-15 word
   clause ("Issue one forty two is about choosing Redis or Postgres for the session
   cache;"), so TTS still takes about 1 s there. A split at "and"/"but" after 8 words or a
   firmer prompt line would cover it.
5. **Measure real GitHub** once the PAT is in: get_issue now makes two requests at once.
